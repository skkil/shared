# Web pages and interactive documents

Many deliverables ship as web pages: onboarding documents, knowledge guides, reports, decks. They must be calm and easy to read, work offline, and still make sense when a script fails or the page is printed. Start from `assets/templates/web-page.html`, which implements everything below.

## Reading comfort defaults

| Setting | Default | Source |
|---|---|---|
| Body size | 18px (1.125rem) desktop, 17px phones | Butterick: 15–25px on screens |
| Line height | 1.6 English, 1.75 Korean | Butterick: 120–145% for print-like text; screens and Hangul's dense glyphs need more; WCAG 1.4.12: layout must survive 1.5 |
| Measure | 68ch English; 38em for Korean blocks | Butterick: 45–90 characters; WCAG 1.4.8: ≤80 characters, ≤40 for CJK |
| Paragraph spacing | 1em between paragraphs; page must survive 2× | WCAG 1.4.12 |
| Contrast | 4.5:1 minimum for body text, aim for 7:1 | WCAG 1.4.3 (AA), 1.4.6 (AAA) |
| Alignment | Left, never justified | Justified text leaves uneven gaps on screens |
| Headings | Clear size steps (about 1.25 ratio), informative text, sentence case | `standard.md` |
| Table of contents | For pages longer than three screens; sticky on wide screens, collapsible on phones | Long pages need a map |
| Korean line breaking | `word-break: keep-all` on Korean text so words aren't split mid-word; `overflow-wrap: anywhere` for long URLs and code | CSS Text |
| Fonts | System stacks that render Hangul well: `"Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR"`, then generic | Offline-safe; Microsoft's Korean guide uses 맑은 고딕 as the Windows default |
| Light and dark | Follow `prefers-color-scheme`, with a manual toggle | |
| Motion | None by default; respect `prefers-reduced-motion` | |
| Print | Expand all dropdowns before printing; hide navigation | |

Never use italics for emphasis in Korean text (Microsoft's guide removes them for readability); use bold sparingly.

## Build rules

- **Self-contained:** one HTML file, inline CSS and JS, images as data URIs. No CDN dependencies unless the user accepts that the page needs a network; then note it.
- **Graceful degradation:** content is in the HTML, not generated by script. Interactive pieces enhance text that already makes sense: an ordered list becomes a stepper, a table becomes a sortable table, an SVG diagram gains click targets, and a `<noscript>`-safe description sits beside it.
- **Restylable by Rebecca:** all colors, fonts, sizes and spacing come from CSS custom properties on `:root` (`--ink`, `--paper`, `--accent`, `--font-body`, `--measure`…). Content never carries inline styles. If Rebecca's `.design/DESIGN.md` defines tokens, map them onto these variables.
- **Accessible:** landmarks (`header`, `nav`, `main`), one `h1`, heading levels in order, alt text on every informative image, `aria-label` on icon buttons, visible focus, keyboard operation for every control, `lang` attributes (`lang="ko"` on Korean blocks so screen readers switch voices).
- **Plain look:** avoid the template tells that mark generated pages: everything centered, purple gradients, one border radius on everything, identical cards (Anthropic's web-artifacts-builder and frontend-design skills). A document should look like a well-set document.

## Source excerpts

Each cited point can carry its full source section in a collapsed `<details>` block that the reader opens, reads and closes without losing their place. Vanessa never types these. Write a placeholder `<!-- excerpt:X12 -->` next to the point, list the locator in `excerpts.json`, then:

```bash
python scripts/extract_excerpts.py inject page.html excerpts.json --sources .vanessa/work/<task>/sources.jsonl
python scripts/extract_excerpts.py check page.html excerpts.json --sources .vanessa/work/<task>/sources.jsonl
```

The dropdown shows the title, author, location and a link to the original, the verbatim text in its original language, and page images when the section holds equations, tables or figures. Use `show` first to confirm a locator resolves to the right passage.

## Interactive elements: earn their place

Bret Victor's "Explorable Explanations" names three forms: **reactive documents** (the reader changes an assumption and sees the consequence), **explorable examples** (the abstract made concrete enough to build intuition), and **contextual information** (related material just in time). Hohman, Conlen, Heer and Chau ("Communicating with Interactive Articles", Distill 2020) add that interaction can make systems playful, prompt self-reflection, and reduce cognitive load.

Use one only when the reader understands faster with it than without. Test: what will the reader do with it, and what will they understand afterward that the static version couldn't give them? If you can't answer in one sentence, leave it out.

| Element | Use when | Static fallback |
|---|---|---|
| Explorable architecture diagram | A system with more than five components; clicking one shows responsibility, code location, dependencies, failure modes | The components table below the diagram |
| Step-through | A flow or algorithm the reader must follow in order | The numbered list it enhances |
| Simulation with sliders | A cause-and-effect relationship with a real formula from the sources | A table of three example input values and results |
| Runnable or editable code | Small JavaScript examples where output builds intuition | The code with its expected output |
| Self-check quiz | Onboarding and study guides, after each major section | Questions with answers in `<details>` |
| Source dropdowns | Every cited point in knowledge and onboarding documents | They are `<details>`; they work without script |

Every number an interactive element shows comes from a source or a cited formula, like any other claim.
